## Interpretation policy

Owner notes often specify a desired effect and a tentative implementation in
the same paragraph. Editors MUST preserve the desired effect but MAY replace
the suggested mechanism when correctness, evidence, or maintainability demands
it. The replacement and rationale MUST be recorded in an ADR.

Examples:

- “read then clear a buffer” becomes a durable Activation manifest and cursor
  commit, preserving batch processing without data loss;
- a duplicate count moves from immutable Block state to Delivery occurrence
  metadata, preserving multiplicity without mutating shared content;
- AIMD, `tensity`, and automatic association remain experiments because the
  notes explicitly require scientific validation.

## Change workflow

`REQ-GOV-002` — A semantic change MUST include all of:

1. a problem statement and affected requirements;
2. an ADR with alternatives and compatibility class;
3. normative prose and state-machine changes;
4. schema changes;
5. positive, negative, retry, crash-point, and migration vectors;
6. a traceability-table update;
7. an explicit rollback or downgrade result.

`REQ-GOV-003` — A research result MUST NOT directly edit stable defaults. It
first becomes a versioned optional capability and passes the promotion gate.

## Version policy

The specification uses `MAJOR.MINOR.PATCH[-status]`:

- MAJOR changes observable stable semantics or removes a capability;
- MINOR adds a negotiated compatible capability;
- PATCH clarifies behavior without changing valid outcomes;
- `draft`, `candidate`, and `stable` indicate review maturity.

Protocol, config, database, event-journal, Extension SDK, and model-profile
versions are independent but MUST declare their compatibility with the spec
version.

## Decision records

An ADR becomes **Accepted** only after the affected tests exist. Superseding an
ADR never deletes it; the replacement links back and supplies a migration.
