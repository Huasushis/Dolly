## 整体架构是这样的：
基本概念：Page（原来所说的context），Module（即Extension），Block，Premise
接下来我们用Dolly代指这个项目运行时的一个智能体整体。
Dolly本身由若干Page和Module组成。一个Page可以看成一段上下文段，其本身没有长度限制（原来是有的）。一个Page可以看作一个广播空间，广播的单位是若干Block，作为信息的基本单元。
一个Module可以接入若干Page，一部分是输入，一部分是输出，一个Page当然也可以同时是一个Module的输入和输出。数据的运行方式大概就是周期性激活一个Module，把所有输入当前Module的Page的所有新增Block合到一起，作为Module运行的一个输入（也有可能这个module没有任何输入的page），然后Module返回唯一的一个Block（也可以不返回，返回空），作为输出，广播到所有这个Module输出的Page里面（相当于给所有其输出的Page里对应输入的Module广播）。也就是说，对于一个Module来说，其自身连接情况是不透明的。
然后很重要的问题就是这个每个Module的调用周期怎么决定，才能够使得整个网络能够更高效处理数据，不会太慢，也不会太快使得竞争过于激烈。要达成刚好能够错开那样。我通过研究一些认知科学和wifi，子系统的原理，构想了这样的模式，你可以尝试在此基础上进一步思考。目标是尽量让信息（Block）产生的速度和处理的相匹配。

建模大概是下面的样子：
```
图 G = (V, E)，可以有环（Cycles）

每个节点 vᵢ：
  - 速度上限：sᵢ 字节/秒（处理速度）
  - 行为：被调用时，读取缓冲区中【所有】未处理数据（总量 Dᵢ 字节）
  - 耗时：Dᵢ / sᵢ 秒
  - 输出：生成【1 份】数据，大小 ≤ M（M 是全局常数上限，也可以看成M_i，但更复杂）
  - 广播：这份输出被发送到所有出边指向的下游节点

输入节点：没有入边，按外部频率 f₀ 产生数据（每份 ≤ M）
输出节点：没有出边，消费数据

目标：确定每个节点的调用频率 fᵢ，使得每次调用时 Dᵢ 尽量小
```
当然这个目标不一定是这个，但是可以得到Σ f_upstream < sᵢ / M，也就是一个点的频率，应该由其下游处理的速度决定，当然还有网络结构。

如果我们只测量每个Module每次处理数据的时间，发现可以利用类似TCP的AIMD算法。就是检查如果一个module运行完后其新的缓冲区里面数据超过这一轮的，或者其处理时间已经超过其周期了，那么就调低其直接上游的频率（就是公用page的上游module，是输出到page中的，当前这个module是page输入到module的），反之可以调大上游频率（缩小间隔时间）。

也就是现在具体的运行方式：
module视角：然后定周期运行（由主框架调用），每个module有一个缓冲区存page发来的block，运行时取出缓冲区的block，并清空缓冲区（处理的时候缓冲区也可以插block，仅仅在取、清空这一步稍微锁一下）。然后根据各个module功能处理好数据返回一个block/返回空。
框架主体视角：负责调度module的运行，类似于一个**action模型**，每个module初始一个频率/周期，可以稍微加入一些扰动。然后定时运行一个module（**注意**：module不是只在被主框架调用时才运行，其实是一个一直运行的线程，这里及后面所有所说主框架运行module都是指主框架调用了module的一个类似api接口的函数，或者说发起一个通信请求/action操作一类，反正通信模型你自己定，module可以在后台偷偷干自己的事情的）。产生的block根据page网络的关系，看这个module输出端连到哪些page，这些page里面又要输出给哪些module，然后放进这些module的缓冲区。根据后文关于这几个概念的描述，每个block有一个id，这里放缓冲区相同id需要合并，每个block里面可以加一个参数记录次数，有可能会用到，就是说如果两个module通过两个page都练起，那上游的block在这种情况算两次。然后看看需不需要更新每个module的周期/频率。至于一个module的运行，不会出现同时运行两个的情况，绝对是串行的，建议频率/周期记为周期时间，然后每次等待的时间为周期减去运行时间和0取一个max。如果超过周期了在前面的调整方法基础上也可以考虑降低频率/提高周期。这里涉及到很多并行，实现的时候一定要注意锁/死锁问题。我个人想法就是主框架始终串行执行/异步，只有计时器（不知道异步有没有这种功能的定时器）还有module运行的时候可以detach多线程并行，其余比如时间到了调用module（这里取出缓冲区再清空都是在主框架完成的，作为参数传入），一个module运行完了获取返回的block（如果有）更新周期，然后写入缓冲区，这三个主要功能，主要是缓冲区的锁还有记录每个module周期的锁（周期可以在修改的下一次生效，不需要在当前module轮立即生效，如果当前module处于等待期间的话，意思就是可以直接修改）。实际框架可能还有更多用于管理的功能需要实现，这个你后面自己看。


接下来是对这几个概念的描述，Page不用说了，相当于建立了一个A集合到B集合两两有向边，不过A和B可以有交集。具体实现的时候缓冲区不一定是真每个module做一个缓冲区，只要功能相同即可，**这一点原则在其他地方也可以适用**，比如可以每个page维护只维护一个block的序列，对应要输出到的module各自维护一个指针就行，总的缓冲区就可以把一个module的几个page的尾巴上的合起来，可以按照时间顺序，比如在block里面放一个记录，可以记时间也可以放计数器之类的，反正主框架里面获取block都是串行的对吧。page的话最前面那个指针移动了把没有用的最前面的去掉就好了，注意不要内存溢出。

然后是Module，Module看成extension运行产生的实例，为了方便与拓展，我认为一个extension可以产生很多功能相同的module，相当于复制了很多份运行，配置也可以不同，因为module运行过程可能会有一些内部的状态或者外部状态，每个extension生成的module可以有一个名字，可以自定义，也可以是加上后缀什么的来区分，反正在后面配置文件描述里面说。每个extension可以有一个自己的目录，用来存公共数据什么的，每个module也有一个隔离的目录，可以根据module的名字来（注意module的名字和extension的名字有区别）。隔离的可以防止本来的xxx/extension-name/{一个名字，我不知道怎么取}/{这个module的一个名字}，公共就用xxx/extension-name就行了，xxx是项目下一个目录吧，你自己定。

接下来是Block，就是一个module产生的数据，是一个json。里面首先有一个id，这个id应该是一个二进制串，实际可以用一串十六进制字符串，随便随机数/uuid/哈希之类都行，你自己选。和前面说的一样，还可以有一个时间的标识。对于输入的block，还有一个参数是重复的次数。不过这三个是由主框架添加的，module返回的时候没有这两个key。内容可以看之前版本说的那样：**需要注意，在目前新的这个框架下，原来的forget，sleep之类用不到（至少目前是这样），应该去掉**

{"description": "xxx", "source": "xxx", "data/content": [], "extra_body": none/{}} 这就是module要返回的结果，然后在主框架添加上id和时间标识/count一类的，source也是自己写。这个地方如果你觉得这样结构不好你也可以自行头脑风暴，**这个规划里面所有具体的数据的结构安排都提供参考，你可以设计自己的通信方式**

description作为对消息的描述吧，主要给人/日志看的或者给llm看的,source可以是module的来源，extra_body暂时没有用处，向前兼容的。第三个参数名我还没想好，你可以像一个更好的，主要用来装各种方法和信息，也是结构化的，比如可以写成{"type":"toolcall",xxx},{"type":"send_msg",xxx},{"type":"think",xxx}这一类的，具体type可能有所不同，主要是给其他module处理的时候看有没有匹配的方法。这一类就叫做*方法信息*，就这样叫，原谅我不会取名字，你可以取更好的。

block里面可以包含多模态数据，比如图片，音频等。你可以设计一种最底层的数据项，比如还是{"type":"text","text":"xxx"} {"type":"image", "xxx"}...注意这个和前面方法信息不一样，这个是数据项，但是数据项可以是一个*方法信息*。这里有一个我暂未思考清楚的问题。就是对于文本类型，是否允许就是底层数据项就是不用包装成这样一个指明type的json，直接用字符串表示，即直接用字符串表示type是text这个类型了。具体规范你来定，考虑到代码实现的容易程度与是否对ai友好？这些的，就像大模型openai的api一样。我希望这么进行管理。由于block很多，所以我希望block设计成类似共享指针一样的持有模式，page会持有，module也会持有（就是传入的参数），page用完扔掉，但是module可能还需要之前的block，一个block直到所有指针释放掉才销毁。同样，像图像，音频，视频一类的数据（后面为了方便可能只说图片，这三个都同理），不一定直接只是base64放在block当中。全给主框架进行管理，对于module返回的一个block，这些可以是直接的base64，url或者本地文件file://一类的，但是主框架给他们和block一样也分配一个id，可以看作和block一样指针维护的东西，然后主框架后面分发都是用这个id格式的，比如{"type":"image",xxx}里面xxx就是id，然后提供给module一个方法可以通过id查询到原本的图像（提供不同的方法，比如module可以查询字节流/base64/url等，自动转换，url就是配了oss才有，否则可以报错或者用base64（推荐），这个根据你后面写的extension开发文档规定，或者图片本来就是url格式的，不过如果有oss，且文件不大，最好url还是尝试传到oss更保险防止module用到的其他厂商服务网络环境不同可能会出错）。然后module返回的block里面可以再次引用这个图像/音频/视频的id，同样可以用共享指针，如果销毁了就释放这个图片（如果这个id创建的时候是base64或者url，然后下载缓存到本地；或者将这个多媒体不管最开始是base64/url/本地文件上传到了oss（可有可无，可以看作主框架一个配置），就也要删去）。也就是一个block后续流通里面的多媒体项都变成id了，只有block由module返回的时候可以有原始的表示多媒体的方式。然后对于图像，我希望新增一个额外的功能，就是可以通在json里面引用已有的图片时，支持裁剪，就是可以框出一个矩形。具体是直接用像素还是归一化表示你自己定。即一个module返回一个block时，如果引用了一张已经有id的图像可以直接对其裁剪。第一是节省空间第二也方便llm的使用。

在这里之前的forget一类的没有了，但是block里面content就可以加一种自带的类型，转发类型，是一个*数据项*，也可以作为转发类型，{"type":"forward", "id":"xxx"}，这样的，引用一个block，显然只允许合法的，后来的block才能引用之前的，需要合法，不能自引用，注意生命周期，相当于一个block持有了另一个block的引用。相当于出了前面图像一类的之外额外的一种类型，框架也提供给module一个方法通过id查询block。主框架可以自行剔除一些不合法的，比如引用和图片之类的。或者替换成错误信息一类的。

**block里面还可以加一个项**，叫做tensity，代表强度，目前作用不完全明确。我也不太确定是由module自行生成还是主框架来计算。目前的一个作用第一点表明block的信息重要强度，第二点根据概率建模代表一个block存活的一个大概时长比例，这一点在后面的llm extension会说到。根据其倒数来随机淘汰。是一个浮点数，标准参考值是1.0。具体使用还可以和block里面重复次数结合起来使用。

至于对于llm要怎么使用这些type以及输出这样的方法信息，就是下面premise的概念。

每个运行时的module维护一段premise字符串，module正常运行过程中可以修改。主框架在每次调用module的时候收集module所在所有page里其他module的premise（可以包括自己，就是整个直接上下游的module，都有），然后作为另一个参数传给调用（有一个参数前面不是说了吗，是缓冲区block）。这里premise目前就字符串就好了，没有更加复杂的必要。主要是用来给用到llm的extension用的，教会llm使用其他module提供的方法。更好的是每个module写两个premise字符串，一个是表示自己识别的方法的premise，相当于输入的block里面的方法；第二个是对自己输出的block的描述，拆成两个，这样更好。获取premise也算作module一个方法/函数，主框架依然是在调用一个module的时候挨个询问，当然也可以做成出框架维护的字符串，module调用主框架的方法修改。这个你自己写spec的时候选好的。

还要考虑到可能的多开需求，配置文件里面可以设定一个名字，数据目录存在不同的下面，或者指定数据目录（就是前面说的各个module的数据的地方，还可能有其他信息，比如日志一类的，每个module的调用频率/周期）

### memory

### llm

llm是核心模块，是整个架构的思考核心，承担不同的模块，且之前的mcp需要融合进llm模块了，因为涉及到tool_call，这样提高通信效率。可以配置模型，支持的模态，是否保留上下文等（后面细说），一段自定义系统提示词，还可以配置premise（llm模块可以默认没有premise，可以人工定义，给其他的llm模块看）。这一部分在最开始写的时候主要使用deepseek-v4系列和qwen3.6-27b（如最后注所说，qwen主要是提供了视觉能力，此外，还可以测试音频模型，即文的fun-asr-xxx，前面不是说了裁剪吗，llm可以输出一个图片的裁剪，但是需要注意qwen3.6开源系列的坐标是0-999归一化后的，所以要额外转换，而且不同的模型都可能不一样，所以配置里面大概也应该配置一下，而且还要考虑可能的大模型厂商自动缩放相关的一堆杂七杂八的问题你要尝试解决）你尤其需要关注这几个模型的思考模式、json output结构化输出、tool calls。在这个模块中，尤其更加需要坚定“不要相信任何前端传回来的东西”的原则。大模型的toolcall可能是错误格式，输出的content也可能是错误格式。由于输出是json，所以需要验证，如果不满足，可以另外调用一个无思考的模型来纠正。如果是空那就没有了。

llm的系统提示词是很关键的，这样组成：一个关于本框架的描述，让llm能够返回一个正确的json，即前面block那里所说的那样，而且要让llm理解当前所处的环境要描述清楚。接下来可以接一个用户自定义的提示词，可以用来描述当前这个llm module在整个框架中的具体作用，也可以为空。然后再接下来就是调用的时候传入的所有相邻module的premise（要注意一个module两个premise，根据输入还是输出决定是哪个，也可能都有），拼进去（所以premise相当于一个广义的tool call）。提示词里还应当多鼓励llm提出设问，对自己的问题，对内容的问题，尝试主导整个环境的对话，努力尝试否认其他的对话。

这里额外需要注意图片/多媒体的处理问题。由于视频大多数模型只是截帧，所以考虑到音频转录，可能还需要主框架提供音频拆分的功能？需要用到ffmpeg。对于没有视觉功能的模型需要在系统提示词里面需要指明其没有视觉能力，防止产生幻觉。在具体的上下文里，依旧可以通过单纯文字化的形式，就是像block那样直接给id给llm。这样llm可以通过输出，单独询问图片，或者转发block来向其他模块获取图片信息一类的。

对于有视觉功能的llm，图片也不能直接只给图片，原本图片的id还是要给，然后将图片插在上下文中间，指明图片和id的对应关系。不然会对应不上。

这里当然很重要一点就是怎么把一堆block喂给llm。这里就有一点了，前面说的llm配置是否保留上下文。不保留就是每次只有系统提示词还有新的block，一般可能主要用于处理一些信息，完成特定任务，比如语音转文字的那个。所以llm要通用一点，语音转文字那个应该提取出新的block里面的音频，然后识别返回，可能得特殊做一点。当然不只是语音模型可能用到这种模式。block的指针用完就不要了。

然后就是保留上下文的，也就是说module会持有一定的block。如果超了上下文怎么办了？我的想法是这样。前面不是有tensity吗？我们用tensity来代表一个存活时间的一个倍数关系，通过比较简单的数学建模可以发现，如果上下文满了的话按照tensity的倒数作为权重，然后按照这个作为概率删去，一个block的存活时间大概和tensity成正比。直到不超了。当然不可能上下文全满了才清理的，大概你计算到百分之多少就准备遗忘一些block了。但是这里tensity可以做一些调整，因为前面不是说同一个block可能堆叠吗？所以可以关于次数写一个函数作为时间倍数调整？做一个凹函数（导数减小）类似ln的那种？或者有上限的那种？你可以选一个，调整时间。

**注意**：所以这有一个现实的问题，就是各个module产生的tensity要怎么设置？我认为这个也可以研究一下，一些东西可以低一点，另外一些可以高一点。像包含图片的就可以低一点，或者外部的可以高一点？如果不计成本的话，甚至可以让llm的返回和所有block做一遍rerank根据关联度在llm module内部对tensity进行微调（）不过如果tensity能够像module周期一样动态调整就好了，我这一点主要是想模拟大脑的活动强度。但是注意不要我说动态调整你就非得硬生生整出一个！我这里很多都是实验性的！你得现有理论或者研究支持再给我搞！**原则是：没搞完全清楚的东西一定全都别搞！**。在你最终实验后，给开发者的文档里面也要提到适合的tensity值，比如什么样的东西多少tensity合适（标准值是1，你全部翻倍并不影响概率权重）。这个也不能拍脑袋想！和前面一样，要实验！而且我前面也说了我不清楚tensity是由module设置还是主框架来算，抑或是主框架会调整tensity，总之这需要你帮我头脑风暴一下。这些都是研究性问题，需要思考、实验、验证。

其实有一个问题是怎么把一堆block排成上下文，尤其是user和assistant这种。我有一个思路是在llm里面再抽象一层出来，就是把block拆成更细的一层，比如把一个block的方法拆出来，生命周期再套一层相当于，然后tensity继承过去，可以根据类型微调之类的……但是这样有个缺点是llm无法forward block了，如果llm要回复的话？直接把block的文本放进上下文说不定更好。由于有source，把自己发的放到assistant，其他全放user里面也行。

对于包含forward类型的block，在注入上下文的时候可以考虑展开，设置一个最大展开层数？

然后对于tool call，这里要注意像deepseek在思考模式下是可以调用工具的，qwen我不清楚，你自己查文档，要求是需要回传reasoning_content，多轮请求，这也是为什么把mcp放进llm的原因。llm里面也要配置mcp服务器，注册tool。

注意到deepseek：
在两个 user 消息之间，如果模型未进行工具调用，则中间 assistant 的 reasoning_content 无需参与上下文拼接，在后续轮次中将其传入 API 会被忽略。详见多轮对话拼接。
在两个 user 消息之间，如果模型进行了工具调用，则中间 assistant 的 reasoning_content 需参与上下文拼接，在后续所有 user 交互轮次中必须回传给 API。详见工具调用。

这里需要注意自己也可能收到自己发的消息的block。发出去的消息仅仅是最后一条的content。llm需要管理reasoning_content，还有额外的工具调用返回值，content。就是要注意user之间可能出现的工具调用。如果user里面的block被删干净了的话，要把工具返回，这些都清理掉。deepseek貌似是支持两个assistant或者user连在一起的，其他模型你要具体看。总之做好拓展性或者专门适配。

另外我认为可以把一个控制思考强度的功能注册成一个tool，让llm可以自己控制自己的思考强度。

首先进行横向测试，就是研究这个项目如何组织。接下来有若干我设想的对比实验，你可以考虑更过实际可能的情况：

首先是这两种对比
第一种是主llm直接连接所有外部输入的信息，mcp这些也直接加到主llm上；对比的是相当于一种隔离操作，将主的llm只与其他弱的llm相连，这些弱的llm来使用工具，比如skill和一个llm连接，附属llm上面才挂mcp，memory模块也是，在主llm所在的page只输入，额外添加一个page，附的llm可以输入输出，memory允许输入。相当于只允许附llm查询记忆（我前面理想情况是一个page对应一个memory 的module不是吗？这个memory在这个page可以输入也可以输出，现在相当于变成一个工具调用）。然后顺便可以测试llm能不能自行分工，就是人工给llm分配是干啥的（比如调用工具，审查一类的），看一下能不能自分工，和手动安排角色对比一下。这里就涉及到好几个实验了，我说得很模糊，你具体操作时需要认真设计好实验。
还有一个自我学习实验，看一下特定架构下学习能力。还要检查一些基本的事实记忆能力。比如对话遇到一个人，在过很长时间（上下文几乎刷新），重新遇到一个人能不能自动注入相关记忆，能否形成对一个位置事物（可以是人，也可以是其他概念）的认知和印象，能否记忆一些事实。
